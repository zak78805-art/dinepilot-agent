# 双端聊天会话管理方案（已确认并实现）

## 目标与范围

承接已确认的四个方向：回收闲置会话、限制会话数量、本人清空当前对话、并发时保护正在使用的会话。继续离线开发，不启动业务服务，不调用真实模型、Java或数据库，不修改JWT密钥及Token有效期。

## 实现选择与建议默认值

推荐沿用当前单进程内存存储，不接Redis。内存管理可以直接在现有代码上离线验证；Redis持久化涉及额外部署和多进程一致性，不纳入本轮。这是实现建议，不宣称已经完成。

建议新增可配置项：`AGENT_SESSION_IDLE_SECONDS=1800`（闲置30分钟），`AGENT_SESSION_MAX_ENTRIES=500`（每端、每进程最多500个会话）。两端分开计数，因此单进程合计最多1000个；不是每个用户500个，也不是整个多进程部署的全局上限。配置必须是正整数。以上参数是聊天上下文管理，不是登录有效期。

回收采用访问时清理：下一次聊天或清空请求到来时，扫描并清理闲置超过阈值的条目；不会承诺在无请求时精确到点释放。容量满后只拒绝新的会话，返回503；已有会话仍可继续，不驱逐未过期记录。TTL只从最近一次请求结束计算，使用单调时钟，不受系统时间调整影响。

## 会话与并发规则

将会话实例、锁、最后活动时间及使用计数归到同一个条目，键仍为`(role, verified_actor_id, session_id)`。先登记使用计数，再等待会话锁，因此排队中的请求也受到保护。正在运行或有等待者的会话不能过期回收或删除；同一个会话继续串行执行，不同会话可并发。取消、失败和创建Agent失败均须归还计数，不留下占位或锁泄漏。

过期或清空后移除条目并尝试关闭其模型HTTP客户端，关闭过程有时间上限，失败不输出内部异常详情。清理不能关闭正在运行的模型，也不能使旧锁和新锁同时服务同一条仍在处理的会话。

## 本人清空接口

- `DELETE /api/agent/merchant/sessions/{session_id}`：使用现有管理员鉴权。
- `DELETE /api/agent/customer/sessions/{session_id}`：使用现有用户鉴权。
- 主体ID来自服务端身份核验，不接受请求指定其他用户或角色。只能操作本人当前端的键。
- 路径会话编号沿用1～128位字母、数字、下划线或连字符校验。
- 空闲会话返回200及`{session_id, agent_role, cleared:true}`；不存在或已被回收时200及`cleared:false`，不泄露其他主体同名会话是否存在。
- 正在运行或排队时返回409，不强行中断。相同ID随后重新聊天将创建新的上下文。

本轮只交付后端接口，既有商家网页的“新会话”仍是换ID，不自动宣称已经调用服务端清空；页面按钮下一轮再接。

## 验证与非目标

用可注入的虚拟时钟、Event和内存HTTP模拟验证：TTL边界与续期、满容量时已有/新会话、隔离、活跃和等待者保护、取消、异常、创建失败、资源关闭，以及DELETE鉴权/归属/409/幂等。不得用长时间sleep或启动服务验证。

不做Redis、跨进程全局配额、会话内容字节上限、完整限流、排队请求数上限、Token撤销、业务数据删除或写工具审批。清空只移除Agent进程中的上下文，不删除原订单、审计日志或模型供应商侧可能保存的数据。真实模型质量、部署和联调仍未验证。
