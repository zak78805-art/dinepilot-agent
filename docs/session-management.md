# 会话管理代码说明

本轮实现1800秒闲置TTL、每端每进程500条容量，以及本人清空API；默认值可配置，不涉及JWT密钥或Token有效期。使用现有内存实现，不启动服务，不增加Redis或依赖。

## 代码怎么配合

- `app/memory/session_store.py`把实例、锁、使用计数和最后活动时间放在同一个条目。`use()`先登记计数，再做异步清理和等待会话锁；所有退出路径都归还计数。工厂创建失败且无等待者时移除占位。TTL、容量只作用于条目；不是上下文内容字节上限或完整限流。
- 访问时清理过期空闲条目，不清理正在回答或排队的记录。先关闭过期实例再等待当前锁，防止请求帧积存已移除但仍引用的实例。关闭尽力执行，默认等待2秒，关闭协程必须响应取消；失败仅给固定告警，不输出异常详情。
- `app/agent/merchant_agent.py`让商家与继承的用户Agent各持有独立Store，键为端、认证ID、会话ID。移除了原来绕过管理的私有缓存入口；聊天语义、工具与权限不变。
- `app/api/routes.py`从既有身份依赖取得主体ID，容量满映射503，清空忙碌映射409。用户不能通过参数选择其他人的会话。具体请求和响应见`dual-agent-api.md`。
- `app/config.py`和`.env.example`提供默认配置；没有修改真实.env。

## 商家网页接入

- `web/core.mjs`通过现有同源代理发送本端DELETE，只在请求头传递管理员凭证。核对响应端、会话编号及布尔结果；聊天和清空共享请求锁，不能同时发送。
- `web/app.mjs`点击「新会话」先确认清空当前对话和未发草稿。成功或会话已不存在才清页面并换编号；忙碌、网络故障或超时保留页面内容。超时无法判断服务端是否已清空，可手动重试；清空不存在的会话不会报错。登录凭证变化时仍隔离页面状态，忽略上一凭证迟到的结果。
- 通过Node模拟HTTP请求和页面事件验证流程，不启动浏览器或服务。没有修改用户端页面、JWT、Java后端或部署配置。

## 并发与异常验证

测试使用虚拟时钟和Event，不用真实模型、数据库或长sleep。覆盖TTL边界/续期、容量、持有者与等待者、取消、工厂/回答异常、资源关闭失败与超时、主体隔离及清空接口鉴权/幂等。

只读审查发现“过期资源留到当前回答结束才关闭”的重要问题；先加测试观察到失败，再修为等待锁之前关闭并释放退休列表引用，完整套件回归通过。每端单进程内使用同一事件循环；不提供跨事件循环共享或多进程全局一致性。

清空与过期仅移除当前进程的Agent上下文，不删除订单、日志或供应商数据；不取消运行中的回答。没有会话内容字节限制、排队数量限制、全局限流、持久化或用户端页面。本轮离线通过不代表实际模型或部署联调已验证。

最终离线验证：Python205项、Node18项、Java身份7项通过，契约导出及编译检查通过；没有启动业务服务。原177项基础上新增28项会话专项回归。
